comparison point, not a bit-for-bit reproduction of the historical image.

## Stack under test

- One `fraud-rule-engine:local` application container using the `local`
  profile and Java 21.
- One `postgres:17-alpine` database container.
- Hikari maximum pool size of 5 and minimum idle size of 1.
- OpenTelemetry traces, metrics, and logs exported to the running
  `grafana/otel-lgtm:0.27.1` container during the test.
- Docker Desktop 29.6.2 on ARM64, with 8 virtual CPUs and approximately
  3.83 GiB available to Docker.
- No explicit CPU, memory, or PID limit was applied to the application
  container.
- The k6 runner executed in a separate Docker container and reached the app
  through `host.docker.internal:18080`.

The JVM and database were warm because a 5 iterations/second, 10-second smoke
profile ran immediately before the recorded profile.

## Independent persistence check

After k6 exited successfully, PostgreSQL was queried independently:

```sql
SELECT count(*)
FROM transaction_event
WHERE event_id LIKE 'load-event-evidence-20260803-local-final-%';
```

Result: `1201`. This matches the k6 successful-write count.

The application logged one PostgreSQL `SQLSTATE 40001` serialization warning
during the run. The configured transient-database retry path recovered it: the
client received no failed response, all response assertions passed, and all
1,201 rows were present after the run. No retry was exhausted; no
`FRAUD_PROCESSING_FAILURE` log signal or `PROCESSING_RETRY_EXHAUSTED` response
was observed.

## Reproduce

From the repository root:

```bash
FRAUD_APP_PORT=18080 FRAUD_MANAGEMENT_PORT=18081 docker compose up --build --detach --wait

docker run --rm \
  --add-host host.docker.internal:host-gateway \
  --volume "$PWD/load-tests:/work" \
  --workdir /work \
  --env BASE_URL=http://host.docker.internal:18080 \
  --env RATE=20 \
  --env DURATION=60s \
  --env RUN_ID="local-$(date -u +%Y%m%dT%H%M%SZ)" \
  --env SUMMARY_PATH=/work/results/latest-summary.json \
  grafana/k6:2.0.0 run k6/transaction-ingestion.js
```

The command returns a non-zero exit code if any threshold fails.

## Limits and next test

This baseline does not include TLS, ALB, WAF, Cognito, ECS networking or task
limits, RDS, cross-AZ latency, production-sized data, a hot-customer velocity
pattern, autoscaling, task termination, or dependency failure. Its short,
warmed, unconstrained local run is useful for regression comparison but not
for choosing production capacity.

Before a production release, first add Cognito-compatible authentication to the
scenario, then repeat it in an isolated staging AWS environment against the
immutable release image. Add a longer soak test, a step/ramp test to find
saturation, representative customer reuse for the velocity rule, and
ECS/RDS/ALB resource telemetry. Agree the 20 writes/second target and 500 ms p95
objective with product and platform stakeholders rather than treating these
sample thresholds as business requirements.
